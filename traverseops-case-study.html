01 / Summary

A workflow demo built around records, maps, and follow-up work.

Field-operations teams lose time when location, records, workflow state, and team permissions are split across disconnected spreadsheets, map viewers, and ticket lists. I built TraverseOps to show how a MapLibre map, Supabase-backed sample data, selected-asset context, inspection flows, work orders, imports, reports, and role-aware screens can fit together in one usable public demo.

Technical problem

Asset location, inspection history, work-order state, imports, reports, and team roles need to stay connected around the selected field record.

Constraints

The public demo uses sample data and cannot assume real municipal auth, offline sync, audit trails, or production GIS feeds.

Approach

I modeled the app around a MapLibre workspace, Supabase-style relational data, status filters, selected-asset panels, and direct inspection/work-order paths.

Tradeoff

The demo favors workflow clarity and reviewer access over production infrastructure such as enforced permissions, audit logging, and offline conflict resolution.

Next improvement

Production hardening would add real RBAC, offline sync, import validation, audit logs, field-device testing, and reliable map data sources.

Hiring signal: The project demonstrates product modeling, map UI decisions, multi-entity data thinking, field-device workflow design, and awareness of what would need to change before production use.

03 / Problem

Field crews need shared context at the asset, not after the fact.

A hydrant-style asset workflow can break down when crews use one tool for maps, another for asset records, another for inspection notes, and another for work orders. The result is duplicated typing, delayed updates, uncertain asset status, and weak handoff between the person in the field and the person assigning or reviewing work.

TraverseOps addresses that by treating the map as the entry point and the asset record as the hub. From one selected asset, the user should be able to see the location, understand condition/status, record an inspection, create a work order, and later report on the operational picture.

04 / Target users

Who the interface is designed for

Field technicians

Need fast asset lookup, mobile-friendly detail views, checklist-driven inspection entry, and clear next actions while standing near the asset.

Supervisors

Need to review condition trends, assign or prioritize work orders, and understand which assets need attention without reconciling scattered notes.

Operations administrators

Need import tools, reporting views, team roles, and confidence that changes are traceable before the system becomes operationally critical.

05 / Workflow overview

The core loop starts on the map and ends in accountable work.

  1. Find an asset Use the map, filters, or asset list to locate the hydrant-style record.
  2. Review context Open the selected asset panel to see status, location, type, inspection history, and open work.
  3. Record field activity Create an inspection with condition, checklist results, notes, and follow-up flags.
  4. Turn issues into work Create or update a work order, assign responsibility, set priority, and keep the record tied back to the asset.
  5. Report and improve Use reports to spot overdue inspections, unresolved work, import exceptions, and asset status by area.

In plain terms: the demo keeps all public data inside a sample-data boundary. Users start from a role-specific field or admin context, import or review asset records, use the map to select an asset, then create inspections and work orders from that selected record. Reports and admin views summarize the same sample records so the workflow can be evaluated without exposing real municipal data.

  • The map layer answers where the asset is and which status or area needs attention.
  • The inspection and work-order layers answer what happened in the field and what follow-up work exists.
  • The reporting/admin layer answers what supervisors need to review across assets, imports, roles, and open work.

08 / Data model

The data model is workflow-shaped.

Inspections Asset ID, inspector, timestamp, checklist values, condition, notes, follow-up flag. Captures what was observed in the field and creates an auditable operational history.

09 / Import workflow

Imports are treated as a validation workflow, not a blind upload.

A production field system often starts with legacy spreadsheets or GIS exports. TraverseOps frames imports as a step-by-step workflow: choose a file, map incoming columns to known fields, validate coordinates and IDs, preview rejected rows, then commit validated records into the asset registry.

  • Column mapping makes the import explainable instead of assuming every source file already matches the target schema.
  • Validation catches missing coordinates, duplicate IDs, unknown asset types, and invalid status values before records reach the map.
  • Import summaries create a review point for administrators and a future audit trail for production use.

10 / Inspection and work-order flow

Inspections create operational decisions.

The inspection flow is designed around field decision-making. A crew member selects an asset, records condition and checklist information, adds notes, and flags whether follow-up work is required. When follow-up is needed, that inspection can become a work order tied back to the same asset.

Inspection entry

Captures condition, pass/fail style checks, notes, and field context close to the selected map asset.

Work-order creation

Converts inspection findings into a prioritized task with status, assignment, due date, and source record.

Status visibility

Keeps open work and inspection freshness visible so supervisors can prioritize by asset, area, or urgency.

11 / Demo limitations

The public demo is intentionally bounded.

  • Uses sample data only; it is not connected to a live municipal dataset or active field crew.
  • Role and permission concepts are represented for product clarity, but production authorization would need real authentication and server-side policy enforcement.
  • Import flows should be treated as product/UI proof, not as a guarantee that arbitrary operational files are safe to upload.
  • Offline sync, GPS permission handling, photo attachments, and conflict resolution would need deeper production engineering before field deployment.
  • The public page does not currently expose a public TraverseOps source repository link.

12 / Production hardening plan

What would need to change before real deployment

The public TraverseOps demo proves the product shape and workflow model. A production field-operations system would need stronger guarantees around identity, authorization, data quality, offline behavior, security, and operational recovery before real crews or municipal records depended on it.

Authentication

Real accounts and role permissions

Demo: shows field crew, supervisor, and admin-style workflows.

Production: add authenticated accounts, server-enforced roles, row-level permissions, least-privilege access, session expiry, and clear boundaries for who can inspect, assign, import, approve, or delete records.

Offline sync

Field reliability in poor connectivity

Demo: communicates a mobile-friendly workflow shape.

Production: add offline inspection drafts, retry queues, conflict detection, sync status, background recovery, and user-visible warnings before a crew leaves an area with unsynced work.

Validation

Strict data and workflow rules

Demo: uses curated sample records to explain the asset, inspection, and work-order lifecycle.

Production: validate required fields, coordinates, status transitions, priority values, due dates, duplicate assets, and work-order state changes on both client and server.

Audit logs

Traceability for operational changes

Demo: models records that would be auditable.

Production: record who changed each asset, inspection, import, assignment, status, and report-sensitive field, with timestamps and immutable history for accountability.

Error handling

Recovery paths instead of silent failure

Demo: focuses on the intended happy path and product structure.

Production: handle failed saves, map load failures, permission denials, stale records, sync conflicts, rejected imports, and retry exhaustion with clear messages and safe fallback states.

Imports

Defensive import validation

Demo: frames imports as a workflow concept.

Production: add file type limits, schema mapping, row previews, duplicate detection, coordinate checks, rollback plans, rejected-row exports, import audit trails, and permission checks for bulk changes.

Mobile QA

Real field-device testing

Demo: uses desktop/mobile layouts and field-oriented screens.

Production: test on actual phones/tablets, gloves/wet-screen scenarios where relevant, GPS permissions, battery constraints, camera/photo attachments, sunlight readability, and intermittent network conditions.

Security

Protect operational records

Demo: uses public-safe sample data.

Production: protect real asset data with TLS-only access, secret management, rate limits, abuse protection, secure file upload handling, dependency patching, backups, and privacy-aware logging.

Map data

Reliable basemaps and asset sources

Demo: shows how asset location and status drive the interface.

Production: define map tile/provider SLAs, cache strategy, fallback basemaps, geocoding limits, coordinate-system expectations, asset-source ownership, and alerts for stale or missing map data.

13 / Testing and QA notes

The demo is manually tested around workflow risk and field-device assumptions.

Automated tests

No public automated test suite is linked for the TraverseOps demo yet. The current QA evidence is manual browser testing, responsive checks, and documented production-hardening work.

Manual checklist

Verify loading/resetting sample data, switching roles, opening each tab, selecting map assets, filtering status groups, entering inspection/work-order details, staging import rows, and reviewing report summaries.

Browser and device checks

Check the map workspace, forms, tabs, and action buttons at narrow phone, tablet, and desktop widths. Keyboard focus order, touch target size, live status updates, and reduced-motion behavior are part of the review.

Edge cases

Exercise empty sample data, repeated reset/load actions, invalid import-style rows, missing selected assets, filters with few results, role changes mid-workflow, and long notes/status labels that could stress the UI.

Known limitations

The demo does not yet have automated E2E tests, real GIS data validation, offline conflict simulation, authenticated permission tests, or device-lab testing against actual field phones/tablets.

14 / Deployment and run notes

The public demo runs as a static browser app with sample data.

Hosted/run location

The case study and demo are hosted on GitHub Pages under zacbatten.me. The public demo runs client-side from traverseops-demo.html and traverseops-demo.js; sample assets, inspections, and work orders are bundled in the static JavaScript.

Environment/config

No public environment variables are required for the sample demo. The visible role selector, filters, imports, reports, and forms operate against in-browser sample state rather than a live backend.

External APIs/services

The case study explains a MapLibre/Supabase-style architecture, but this portfolio demo does not connect to real municipal records, private GIS services, or a production Supabase project.

Local development

Clone the portfolio repository, run python -m http.server 8000 from the repo root, then open http://localhost:8000/traverseops-demo.html or /traverseops-case-study.html. There is no build step.

Secrets and data safety

No secrets belong in the static page. A real deployment would keep Supabase service-role keys, GIS credentials, user accounts, and municipal records out of client code, enforce row-level permissions server-side, and validate imports before storing them.
