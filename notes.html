2026-05-09 Web Paint

Building a browser canvas editor without a framework

Date
May 9, 2026
Related project
Web Paint browser canvas drawing tool
Problem
A browser drawing editor has to feel immediate while keeping tool settings, pointer input, canvas pixels, history, imports, and export actions predictable in plain JavaScript.
Tool state
Web Paint keeps the canvas pixels as the document source of truth and uses JavaScript state for the active tool, brush size, colors, selection bounds, zoom level, drag start, pending preview, and status messages.
Canvas rendering
Pointer events are converted from screen coordinates into canvas-space coordinates, then committed through the Canvas 2D API. Shape previews and resize work are scheduled around interaction state so the final pixels are only committed when the action ends.
Undo/redo
History uses capped ImageData snapshots after meaningful commits. That model is simple and reliable for a static editor, with the tradeoff that large canvases can make every snapshot expensive.
Import/export
The tool validates image type, file size, and pixel count before drawing imports onto the canvas. Export paths use PNG download, clipboard APIs where available, local save/load, and fallbacks when browser permissions are limited.
Text and shape tools
Text, rectangle, circle, line, fill, pencil, eraser, and selection modes share the same state loop: capture the starting point, preview the draft interaction, then commit final pixels and save history.
Mobile/touch constraints
Touch drawing needs large controls, compact panels, stable canvas sizing, pointer capture, and touch-action: none on the drawing surface so the browser does not treat a stroke as page scrolling.
Accessibility limitations
The shell uses labeled controls, visible focus states, status output, and grouped tool controls, but the drawing itself is still pixel data. A stronger version would need keyboard drawing shortcuts, a structured layer/object model, and better nonvisual descriptions of canvas content.
Technical takeaway
Without a component framework, the hard part is keeping event handling, UI state, pixel commits, history, and browser API failures small enough to reason about.

2026-05-09 TraverseOps

Designing a field-operations demo around maps, inspections, and work orders

Date
May 9, 2026
Related project
TraverseOps field-operations map and work-order demo
Problem
Field operations break down when crews locate assets in one tool, record inspections somewhere else, and turn follow-up work into notes that have to be reconciled later.
Why maps help
A map-first interface makes location the organizing layer. Crews can find nearby hydrant-style assets, see condition at a glance, select one record, and move into inspection or work-order tasks without losing spatial context.
Asset state
The demo treats each asset as a record with identity, location, status, inspection history, and open-work indicators. Status filters keep the map useful when there are too many points to scan manually.
Inspections
Inspection screens model the field workflow: pick an asset, record condition, capture notes, and leave a timestamped trail that can explain why an asset changed from normal to attention-needed.
Work orders
Work orders turn inspection findings into assignable follow-up. The important design choice is connecting the task back to the selected asset, current status, and supervisor-style review flow instead of treating it as a disconnected ticket.
Imports
The import flow is framed as a sample-data boundary: real systems would need schema checks, duplicate detection, coordinate validation, rollback behavior, and clear feedback before new asset rows are allowed onto the map.
Empty states
Empty states matter because field tools often start with no selection, filtered-out results, missing reports, or no work assigned. The demo uses those moments to explain the next valid action instead of leaving a blank panel.
Production hardening ideas
A production version would need real authentication, role permissions, offline sync, audit logs, import validation, stronger error handling, security review, mobile field-device testing, and dependable map/data-source operations.
Technical takeaway
The useful part of TraverseOps is not only rendering points on a map; it is tying spatial context to state changes, inspection history, follow-up work, and operational guardrails.

2026-05-09 MovieBot

How the Twitch MovieBot turns chat votes into OBS playback

Date
May 9, 2026
Related project
StreamCinema Vote Bot / MovieBot
Problem
Running a Twitch movie night by hand means reading chat, counting votes, resolving ties, finding the local movie file, and updating OBS while the stream is live.
Chat command flow
Viewers send commands such as !vote title, !results, !currentmovie, !time, and !movies. TwitchIO routes each command into Python handlers that validate poll state and command arguments before touching playback state.
Vote state
The bot keeps a per-viewer vote map and aggregate movie totals. When a viewer changes their vote, the old title is decremented before the new title is counted, which prevents duplicate votes from inflating results.
Tie handling
When a poll closes, the bot sorts by vote count, detects tied leaders, and chooses between tied titles with a fallback random selection. If nobody votes, it can pick a random available movie instead of stalling the stream.
Movie folder scanning
The movie scanner walks the configured local folder for supported video extensions, refreshes the in-memory catalog during long sessions, avoids following symlinks, and falls back gracefully when duration tools or files are unavailable.
OBS WebSocket control
After a winner is selected, the bot normalizes the local path, updates the configured OBS media source through WebSocket, switches to the movie scene, and restarts playback so the selected public-domain file becomes the stream output.
Token refresh/reconnect
Long sessions need recovery paths, so the bot validates and refreshes Twitch OAuth tokens, watches the Twitch IRC connection, wraps OBS calls with connection checks, retries media handoff, and cleans up scheduled tasks during shutdown.
What changed
The portfolio now explains the bot as an automation pipeline rather than just a chat command project: chat input, state management, local file discovery, OBS control, and reconnect behavior are shown as one system.
Technical takeaway
The interesting work is not the command syntax; it is keeping chat, local media, OAuth, OBS WebSocket calls, and failure recovery coordinated in a long-running Python process.
What would improve next
Add an operator dashboard, dry-run mode, structured logs, health indicators for Twitch/OBS, stronger integration tests, and safer queue controls for live stream operations.

2026-04-30 MovieBot

Stream room and searchable voting catalog split

Date
April 30, 2026
Related project
StreamCinema Vote Bot / MovieBot and Movie Library
Problem
The live Twitch room and the movie queue were trying to serve different jobs: watching the stream, reading bot commands, browsing titles, and copying valid vote text.
What changed
Kept movie-night.html focused on the stream, chat, bot flow, and fallback links, then moved title discovery into movie-library.html with JavaScript search, result counts, lazy posters, copyable !vote commands, and a complete no-JavaScript list.
Technical takeaway
Separating operational views from browsing views keeps static pages simpler, improves mobile usability, and gives the bot system clearer boundaries for QA, fallback content, and future data generation.

Date

Problem
